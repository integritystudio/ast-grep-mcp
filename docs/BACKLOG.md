### Correctness of the new code

- [x] **BUG-06-CR-03** (P2) Abandoned worker mutates candidate dict after timeout — `analysis_orchestrator.py:481` submits the *shared* candidate dict; on timeout the main thread stamps error fields and returns, but `shutdown(wait=False, cancel_futures=True)` (`:492`) only cancels never-started futures. **Reproduced:** candidate at return `{'test_coverage_error': 'Operation timed out after 1s', 'has_tests': False}` mutated after the leaked thread finished to `{'test_coverage': {...}, 'has_tests': True}` — a contradictory payload written into the exact dicts `_build_enrich_result` returns (`"candidates": top_candidates`), racing downstream stages and MCP JSON serialization (worst case `RuntimeError: dictionary changed size during iteration`). Fix: workers write to a private copy/result holder; merge onto the candidate only when `result()` succeeds.
  - **Fixed 2026-07-25:** both enrichment paths submit `copy.deepcopy(candidate)`; the copy merges onto the original only on success (`candidate.update(working)`), so an abandoned worker mutates only the orphaned copy, and an enrich_func that mutates then raises leaks no partial writes. Accepted trade-offs documented: key deletions don't propagate; nested-value identities replaced on merge. Uncopyable candidates fail alone (routed through the per-candidate error path) rather than aborting the stage. Tests: `TestAbandonedWorkerIsolation` (5 tests). **Adversarially verified** (3 lenses): stress probe 30 rounds × 24 candidates × 8 workers found zero leaked/torn merges; happens-before edge via the future's condition lock confirmed; both production enrich funcs safe with shared kwargs. Side effect: the harmful half of CR-06 (late-run overwriting error state) is neutralized — its wasted-work/mislabeling half stays open.

  - **Fixed 2026-07-25:** `map_with_per_item_timeout` internals rewritten — `ThreadPoolExecutor` replaced with daemon `threading.Thread` workers pulling `(Future, item)` pairs from a `queue.SimpleQueue`, delivering results through manually-created `concurrent.futures.Future` objects (`set_running_or_notify_cancel` gate preserves the CR-06 cancelled-never-runs guarantee; `set_result`/`set_exception` preserve wait/error semantics). Hung threads still accumulate while the process lives — inherent (threads cannot be killed); the long-term fix remains timeouts at the blocking primitive (subprocess/file I/O in coverage detection). **Adversarially verified** (3 lenses + gap sweep, 0 refuted); the three latent issues the verification surfaced were fixed same day: `max_workers < 1` now raises `ValueError` (executor parity), thread spawn moved inside the `try` so a mid-spawn `RuntimeError` still cancels/drains, and the work queue is drained in `finally` so a hung worker's queue reference cannot pin cancelled queued items (weakref regression test in `TestPoolHardening`).
